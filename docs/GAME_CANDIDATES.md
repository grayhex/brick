# Кандидаты на запуск: игры ApolloBrickGames для порта

**Статус:** исследование, PROPOSED. **Решено владельцем (ADR-034, PRD GAMES-04):** первая версия прошивки — **Tetris, Racing, Snake, Tank**; Dice портировать не нужно. Остальные строки таблицы — не утверждённый список для цели «около 10 игр» (GAMES-01, точный выбор OPEN). Данные взяты из закреплённого коммита эталона `abd7c3426f28222b54db2fe280597d7578e7191c` (исходники `src/brick`, `docs/brick/STATUS.md`, `rom-arcade.md`, `library.md`); числа строк — размер кода эталона на TypeScript, а не оценка кода на C и не часы работы. Достоверность — как её заявляет сам эталон; **мы её не перепроверяли**.

Пояснения к таблице:

* **Достоверность.** *ROM* — эталон сверил основной профиль с исполнением оригинального кода (BrickEmuPy, ревизия в `rom-arcade.md`); *донор* — правила проекта n0Live/BrickGame (MIT, [THIRD_PARTY.md](../THIRD_PARTY.md)); *реконструкция* — по описанию, точные параметры не установлены. «ROM» не означает полной побитовой копии: у каждой игры эталон перечисляет, что остаётся допущением. Наши порты наследуют эти пометки и обязаны их нести (AGENTS.md).
* **Кнопки.** Консоль имеет только направления и ACTION (PRD §5). В эталоне `fire` у большинства игр — запасное имя `rotate`; отдельной кнопки огня нет, `needs: ['fire']` у одного Jig Saw. «ACTION как огонь» означает, что игра играбельна без новой кнопки.
* **Сложность** — относительная (S/M/L) по числу механизмов, которые нужно перенести сверх уже готовых (`bk_game_t`, сценки, события, рендер).

## Что уже есть в ядре и чего не хватает

Готово (Tetris, [GAME_TETRIS.md](GAME_TETRIS.md)): фазы партии, счёт и рекорд, скорость и уровень, сценки без ввода, анимация конца игры, события звука, миниатюра. **Перенесено вместе со Snake** ([GAME_SNAKE.md](GAME_SNAKE.md), ADR-033): жизни (до четырёх) и их индикатор, потеря жизни и победа, сценка очистки поля (60 тактов), переход уровня со ростом скорости, накладка `overlay`; всё в `core/game.c` и общее для остальных игр. **Не портировано из `BrickBase`:** дополнительные жизни за очки и «взрыв поля» отдельных игр.

## Рекомендация по порядку

1. ~~**Snake** — вторая игра.~~ **Сделано** (ADR-033, [GAME_SNAKE.md](GAME_SNAKE.md)): основа с жизнями и сценами вынесена в `core/game.c`, сверка по тактам (72 сценария), каталог из двух игр проверяет листание, миниатюры и рекорды по паре игра + вариант. Исходное обоснование: самый маленький набор правил с ROM-подтверждением основного профиля; не требует вращения и новых кнопок; перенос жизней и сценок из основы нужен всем остальным играм, а Snake проверит их на минимуме правил. Одновременно впервые проверит многоигровое меню (листание влево и вправо, миниатюры, рекорды по паре игра + вариант), которое с одной игрой не нагружается.
2. **Racing**, затем **Tank** — остаток первой версии прошивки по указанию владельца (ADR-034). Racing проще (дорога, препятствия, ускорение); Tank — самая большая игра списка (уровни, ИИ врагов, пули, штаб), поэтому после Racing. Обе — реконструкции по донору, не ROM: правила помечаются как приближение. Перед началом каждой определить, нужна ли арифметика с плавающей точкой (см. ниже), и записать допущения.
3. Всё остальное (Honeybee, Frogger, Arkanoid / Pong, Space Invaders, Construction, Pentix) — не в первой версии; порядок и состав до цели «около 10» определяет владелец. **Dice** не портируется.

Порядок после первой версии — предложение для владельца; он же выбирает остальные игры до цели «около 10» (PRD §8).

## Наблюдения, влияющие на порт

* **Таймеры с дробным остатком.** Темп Snake в эталоне — миллисекунды × 60 / 1000 тактов с переносом остатка (`timer -= period`), как у гравитации Tetris (ADR-024: целочисленная замена расходится на «ничьих»). **Решено для Snake:** `double` + побитовая сверка, как у гравитации ([GAME_SNAKE.md §5](GAME_SNAKE.md)); на Cortex-M4F не запускалось (R-1). Для остальных игр с дробным темпом ожидается тот же выбор.
* **Плавающая точка в остальных играх.** У большинства игр десятичные литералы единичны (танковый ИИ — девять); ни одна не использует `Math.sqrt/sin/cos`. Для каждой игры перед портом проверить, где они влияют на состояние; общий вывод для MCU сделать нельзя без измерения soft-double на целевом процессоре (R-1).
* **Жизни и сценки.** Перенос `BrickBase` (жизни, `lose`, `win`, `overlay`, сценки) — общая зависимость; **сделан** в основе, а состояние сценки (поле с накладкой, фаза, события) входит в дайджест сверки на каждом такте.
* **Размер состояния.** Состояние Tetris 552 Б, лимит `BK_GAME_STATE_MAX` 2048 Б; Tank и Invaders могут его превысить: проверять при порте, не заранее.
* **Лицензии.** Правила донора — MIT (уведомление уже в THIRD_PARTY.md); у самого ApolloBrickGames **нет файла LICENSE** (R-3). Спрайты и цифры нужно перерисовать или получить разрешение до публичной или коммерческой сборки.
* **Идентификаторы Snake/Pong** из первых задач [GAME_PORTING.md](GAME_PORTING.md) §6: `snake` и `pong` в `LIBRARY_IDS` эталона (`src/brick/games/library/index.ts`), основной профиль Snake — вариант 01.

## Как проверять порт

По [CONFORMANCE.md](CONFORMANCE.md): записанные трассы ввода, дайджест состояния на каждом такте, регенерация экспортёром из закреплённого коммита, мутационная проверка теста. Для новой игры нужен экспортёр игры: сегодня `tools/conformance/export_tetris.ts` специфичен для Tetris, обобщение — часть задачи второй игры.
