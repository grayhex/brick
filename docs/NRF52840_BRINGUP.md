# nRF52840 DK: сборка системной платформы, измерения, что НЕ проверено

**Дата:** 2026-10-20. **Статус: собирается и проверяется на уровне СБОРКИ; на плате не запускалось.** Это первый шаг [issue #10](https://github.com/grayhex/brick/issues/10): воспроизводимая sysbuild-конфигурация NCS v3.4.1 для `nrf52840dk/nrf52840` — MCUboot, подпись ECDSA P-256 отдельным dev-ключом, слот `slot1` во внешней QSPI NOR, USB CDC ACM для serial recovery (MCUboot) и для MCUmgr/SMP (приложение). Решения и риски — [ADR-042](DECISIONS.md) и R-14…R-17. Архитектура и требования — [MCU_PLATFORM_NRF52840.md](MCU_PLATFORM_NRF52840.md), [FIRMWARE_UPDATE_NRF52840.md](FIRMWARE_UPDATE_NRF52840.md). Код — [`platform/nrf52840/`](../platform/nrf52840/README.md).

> **Ничего из ниже перечисленного не объявляется «работающим», пока не пройдено на реальной nRF52840 DK** ([план испытаний](../platform/nrf52840/tests/HIL_TESTPLAN.md)). Нет прошивки платы, нет логов UART, нет измерений времени обмена и тока — их в этой среде нельзя получить.

## 2. Что собрано

**Среда (воспроизводимо):** NCS **v3.4.1** (`sdk-nrf` b20f8619, `sdk-zephyr` 33fa6a7a — Zephyr 4.4.2-ncs, `sdk-mcuboot` 8122be0d), Python 3.12.3, west 1.5.0. Полный список проектов — `platform/nrf52840/ncs-v3.4.1.sources.txt`.
**Компилятор в этой среде:** GNU Arm Embedded **13.2.1** (пакет `gcc-arm-none-eabi` Ubuntu, `ZEPHYR_TOOLCHAIN_VARIANT=gnuarmemb`), **не** официальный набор NCS (Toolchain Manager / `nrfutil sdk-manager`). Размеры из официального набора могут отличаться; перед фиксацией раскладки пересобрать им.

```sh
# один раз: рабочее пространство NCS ВНЕ репозитория (около 3 ГБ)
platform/nrf52840/scripts/setup_ncs.sh ~/ncs-ws          # даёт ~/ncs-ws/ncs и ~/ncs-ws/ncs-venv

# сборка (MCUboot + приложение + dev-ключ при первом запуске)
export NCS_DIR=~/ncs-ws/ncs
export BRICK_TOOLCHAIN=gnuarmemb     # или активированный официальный набор NCS: BRICK_TOOLCHAIN=nrfutil
platform/nrf52840/scripts/build.sh --variant release --build-dir /tmp/brick-release

# проверка результата сборки (49 проверок)
python platform/nrf52840/scripts/verify_build.py /tmp/brick-release --ncs $NCS_DIR --key ~/.config/brick/dev-keys/brick-dev-ecdsa-p256.pem
```

Выход: `brick-dk-initial.hex` (MCUboot + подписанное приложение, внутренняя флеш — для первой прошивки), `nrf52840/zephyr/zephyr.signed.bin` (для обновления по USB), `mcuboot/zephyr/zephyr.elf`, `zephyr.dts` обоих образов.

**Варианты образа** (`--variant`): `release` — подтверждает себя после самопроверки; `noconfirm` — работает, но не подтверждает (MCUboot обязан вернуть старую версию при следующей перезагрузке); `crash` — падает до подтверждения; `hang` — зависает до подтверждения, сторожевой таймер перезагружает. Три тестовых варианта — только для испытаний (план T10–T12), в выпуск не идут. `--sign-version 0.2.0+0` задаёт версию образа для проверки «обновление → подтверждение».

**Ключевые опции** ([`sysbuild.conf`](../platform/nrf52840/sysbuild.conf), [`sysbuild/mcuboot.conf`](../platform/nrf52840/sysbuild/mcuboot.conf), [`prj.conf`](../platform/nrf52840/prj.conf)):

| Что | Значение |
| --- | --- |
| Режим MCUboot | `swap using move` (без scratch-раздела); откат, если образ не подтверждён |
| Подпись | ECDSA P-256; проверка основного слота при загрузке (`BOOT_VALIDATE_SLOT0`) |
| Восстановление | `MCUBOOT_SERIAL` + `BOOT_SERIAL_CDC_ACM` (старый стек USB device — см. R-15); вход: кнопка `mcuboot-button0` (DK: SW1 / `button0`) при сбросе **или** нет допустимого приложения (`BOOT_SERIAL_NO_APPLICATION`) |
| QSPI в MCUboot | `NORDIC_QSPI_NOR`, страница 4096, `BOOT_MAX_IMG_SECTORS=192` (заданно явно, т.к. «авто» не видит стирание внешней флеш — предупреждение CMake) |
| Приложение: SMP | USB CDC ACM (новый стек USB device), `zephyr,uart-mcumgr`; группы только `img` и `os` (+ параметры и тип загрузчика); **выключены** shell, fs, stat, taskstat, echo, settings, enum |
| Консоль/журнал приложения | UART0 (виртуальный COM отладчика J-Link) |
| Сторожевой таймер | запускается в приложении, 5 с; нужен, чтобы зависший неподтверждённый образ откатывался. Таймер nRF52840 нельзя остановить и (как следует из опции `BOOT_WATCHDOG_FEED` в MCUboot) он живёт через мягкий сброс, поэтому MCUboot обязан его кормить во время swap, проверки хэша и ожидания в recovery: `BOOT_WATCHDOG_FEED=y` проверяется сборкой, **поведение на плате не проверено** (T05, T08) |
| Подтверждение | только после самопроверки (слоты читаются, `slot1` ≥ `slot0`, `storage` читается); сразу при старте — **нельзя** |

## 3. Карта памяти DK (из `zephyr.dts` сборки)

Раскладка — **стендовая, не замороженная**: размеры взяты из оценки [FIRMWARE_UPDATE_NRF52840.md](FIRMWARE_UPDATE_NRF52840.md) (128 / 768 / 128 КиБ) и проверены только сборкой. Один файл [`dts/brick_dk_memory_map.dtsi`](../platform/nrf52840/dts/brick_dk_memory_map.dtsi) подключается и к приложению, и к MCUboot; `verify_build.py` сравнивает полученные карты двух образов.

| Раздел (метка DTS) | Устройство | Смещение | Размер | Назначение |
| --- | --- | --- | --- | --- |
| `boot_partition` | внутренняя флеш | `0x000000` | 128 КиБ (`0x20000`) | MCUboot + USB serial recovery |
| `slot0_partition` | внутренняя флеш | `0x020000` | 768 КиБ (`0xC0000`) | работающий образ |
| `storage_partition` | внутренняя флеш | `0x0E0000` | 128 КиБ (`0x20000`) | настройки / профиль BKSV; обновлением **не затрагивается** |
| `slot1_partition` | внешняя QSPI NOR (`mx25r64`) | `0x000000` | 768 КиБ (`0xC0000`) | второй слот, размер = `slot0` |
| (не размечено) | внешняя QSPI NOR | `0x0C0000` … `0x7FFFFF` | 7,25 МиБ | под ресурсы; не XIP-код |

**Геометрия:** внутренняя флеш nRF52840 — 1 МиБ, страница стирания 4 КиБ, блок записи 4 Б. QSPI DK — MX25R6435F, 8 МиБ (`size = 0x4000000` бит), сектор стирания 4 КиБ (`NORDIC_QSPI_NOR_FLASH_LAYOUT_PAGE_SIZE=4096`), `sck-frequency` 8 МГц, `writeoc pp4io`, `readoc read4io`. Слот: 768 КиБ / 4 КиБ = **192 сектора**; `BOOT_MAX_IMG_SECTORS = 192` (запас равен нулю: больший слот потребует и большего значения). Образ в `slot0` ограничен «слот − 1 сектор (swap using move) − трейлер».

## 4. Размеры (измерено на слинкованных образах, gcc 13.2.1)

| Образ | FLASH, Б | % раздела | RAM, Б | Примечание |
| --- | --- | --- | --- | --- |
| MCUboot (USB CDC recovery + QSPI + ECDSA) | **66 156** | 50,5 % от 128 КиБ | 40 832 | RAM включает стек main 16 КиБ; ECDSA — через CryptoCell CC310 |
| Приложение `release` | **85 880** (`zephyr.bin`) | 11,0 % от 778 090 Б | 25 016 | подписанный `zephyr.signed.bin` — 86 032 Б (заголовок `0x200`, TLV-область `0x98`) |
| Приложение, по `size` (text+data): `release` / `noconfirm` / `crash` / `hang` | 85 868 / 85 796 / 85 948 / 85 208 | — | 24 973 | тестовые варианты отличаются на сотни байт; `release` с версией 0.2.0 — 85 884 Б |

Запас MCUboot в разделе — 64 916 Б; запас приложения в слоте — около 676 КиБ (692 208 Б от допустимых 778 240 Б). **Это размеры «пустого» приложения**: `libbrickcore` (около 36 КБ flash при компиляции для Cortex-M4F, [ADR-041](DECISIONS.md)), драйверы LCD/аудио и BLE-стек (BLE даёт сотни КиБ) здесь **не учтены**; для BLE и игр бюджет 768 КиБ надо пересчитать при подключении.

## 5. Ключи и подпись

* Dev-ключ **создаётся локально** (`scripts/gen_dev_key.sh`, по умолчанию `~/.config/brick/dev-keys/`), **в репозиторий не попадает**: `*.pem` и `*.key` в `.gitignore`; `verify_build.py` проверяет, что в дереве сборки нет `.pem`/`.key`.
* Сборка **отказывается** работать с публичным ключом Nordic (`root-ec-p256.pem`) и без ключа: [`sysbuild.cmake`](../platform/nrf52840/sysbuild.cmake) (проверено: обычный `west build` без `build.sh` останавливается с ошибкой).
* `verify_build.py` проверяет: подпись образа проходит с dev-ключом; **не проходит** с ключом Nordic (негативный контроль); открытый ключ, вшитый в MCUboot, — это dev-ключ, а не ключ Nordic.
* Производственный ключ: создаётся **вне** репозитория и вне CI-секретов без отдельной политики; открытая часть вшивается в производственный MCUboot. Плата, прошитая dev-MCUboot, принимает образы dev-ключа — не выпускать.

## 6. Что проверено сборкой, и что — нет

**Проверено автоматически** (`verify_build.py`, 49 проверок на каждой из пяти собранных сборок, плюс негативные контроли: испорченный байт образа, образ под ключом Nordic, расхождение карты разделов — каждый ловится):
идентичная карта разделов в приложении и MCUboot, равные размеры слотов, непересечение, `slot1` в пределах 8 МиБ, `BOOT_MAX_IMG_SECTORS` ≥ секторов слота, режим swap-using-move (не overwrite-only, не direct-XIP), подпись ECDSA P-256, CDC ACM вместо UART для recovery, вход по кнопке, `BOOT_SERIAL_NO_APPLICATION`, запись образа MCUboot целиком в `boot_partition`, образ приложения в `slot0`, SMP только на USB CDC ACM, отключённые опасные группы MCUmgr.

**Воспроизводимость среды:** `setup_ncs.sh` создал рабочее пространство NCS с нуля (3 мин 25 с, 3,9 ГБ), сборка `release` в нём дала **побитно тот же** `zephyr.bin` MCUboot (sha256 `8f70293f…97f`, 66 156 Б), что и в первом рабочем пространстве, с теми же размерами приложения (у приложения отличается только время сборки `__DATE__`/`__TIME__` в журнале). Это сравнение при одном компиляторе и одном dev-ключе; с другим компилятором или ключом двоичные файлы будут другими.

**CLI `tools/dfu/brick_dfu.py`:** 15 тестов логики на имитации устройства (отказ от неподписанных файлов и мусора, загрузка только в слот 1, запрос на пробный запуск, отсутствие подтверждения со стороны утилиты, итог после перезапуска: «подтверждён» / «не подтверждён» / «загрузчик отклонил», recovery пишет в слот 0, выбор порта «приложение»/«recovery»); мутационная проверка 9 из 9. Эти тесты **не проверяют** протокол SMP, USB, MCUboot, плату. Попытка прогнать утилиту против настоящего MCUmgr-сервера Zephyr на `native_sim` **не удалась**: группа `img` не собирается на `native_sim` (нет `CONFIG_FLASH_LOAD_OFFSET`), UART `native_sim` и MCUboot не подходят — это ограничение стенда, а не вывод о работе утилиты.

## 7. Что остаётся непроверенным

Ни одна строка не выполнялась на железе. План — [HIL_TESTPLAN.md](../platform/nrf52840/tests/HIL_TESTPLAN.md).

* Прошивка DK, вывод журнала, реальные размеры в `west flash`, перечисление USB, имя и номер порта на Windows/macOS/Linux.
* Работа MCUboot с QSPI: чтение `slot1`, трейлер, **swap/test/confirm/revert**, **время swap** (768 КиБ через QSPI 8 МГц — не оценено), износ.
* Serial recovery: вход по кнопке и при отсутствии приложения; **загрузка по CDC ACM при испорченном приложении без SWD**; скорость; совместимость с `smpclient`.
* Приложение: что `mcuboot_swap_type()` и `boot_is_img_confirmed()` дают то, что ожидается; SMP по USB CDC ACM (новый стек) на реальном USB; сторожевой таймер и откат при `crash` / `hang`.
* Обрыв передачи; обрыв питания в середине swap (на DK — отключением питания/USB в заданный момент); неверная подпись; образ с другой версией HW (в базовой версии **нет** проверки версии аппаратной ревизии — требование ADR-038 п.10 остаётся в планах).
* Сохранение настроек при обновлении (раздел `storage` не затрагивается, но NVS/ZMS пока не подключён).
* Raytac MDBT50Q-P1MV2, собственная плата, QSPI NOR изделия (16 МиБ), LiPo, USB-C CC/питание, 20–30 ч, реальный LCD — не входят в эту работу.

## 8. Риски и вопросы (дубль в [DECISIONS.md](DECISIONS.md))

| № | Риск | Что нужно |
| --- | --- | --- |
| R-14 | Всё ниже «собирается» ≠ «работает»: MCUboot, recovery, swap, revert, обрыв питания не пробовались на плате | выполнить HIL_TESTPLAN на DK и приложить логи; до этого в чек-листе только «собирается» |
| R-15 | MCUboot в NCS v3.4.1 для nRF52840 использует **устаревший** стек USB device (`USB_DEVICE_STACK`, предупреждение `Deprecated symbol`) и CC310 (`BOOT_ECDSA_CC310`, устаревший символ): может исчезнуть в следующих NCS | проверить на DK; при смене SDK заново пройти испытания; следить за миграцией на `USB_DEVICE_STACK_NEXT` в MCUboot |
| R-16 | Раскладка 128 / 768 / 128 КиБ — оценка; BLE-стек, игры и драйверы LCD могут не влезть в 768 КиБ слот или потребовать больше `BOOT_MAX_IMG_SECTORS`; изменение раскладки после выпуска опасно | замерить полный образ после подключения HAL и BLE; заморозить раскладку **до** выпуска (ADR-039) |
| R-17 | VID/PID: используются идентификаторы Zephyr (только для разработки). Для изделия нужны собственные VID/PID; строки изготовителя/изделия — «Brick (DEV)» | решение владельца: покупка VID у USB-IF или суб-лицензия через производителя модуля; затем сменить в `prj.conf` и `sysbuild/mcuboot.conf` |
| R-18 | Бинарные блобы CC310 (`nrf_cc310_bl`, лицензия Nordic) и лицензии Nordic-5-Clause в NCS — нужна проверка для коммерческого выпуска | юридическая проверка до выпуска |
| R-19 | Сборка не на официальном наборе инструментов NCS | повторить сборку официальным набором и сравнить размеры |
