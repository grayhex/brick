# Архитектура прошивки: переносимое ядро (прототип 0.1)

**Статус:** PROPOSED (см. ADR-023…ADR-030 в [DECISIONS.md](DECISIONS.md)). Это первый программный прототип: он **не привязан** к дисплею, разрешению, MCU или плате и не выбирает ни одной детали. Все числа о размере — результат *компиляции* для Cortex-M4F, а не измерения на железе.

## 1. Границы

| Входит в прототип | Не входит (сознательно) |
| --- | --- |
| Переносимое ядро на C11 (нет `malloc`, нет глобального состояния, нет ввода-вывода) | Нативное окно SDL (симулятор закрыт терминалом и браузером, [SIMULATOR.md](SIMULATOR.md), ADR-032) |
| Порт **базового** Tetris (вариант 01) + тесты соответствия эталону ([GAME_TETRIS.md](GAME_TETRIS.md), [CONFORMANCE.md](CONFORMANCE.md)) | Остальные 50 вариантов Tetris, Pentix и остальные игры |
| Консоль: заставка, меню, настройки, пауза, рекорды, звук ([UI_MENU.md](UI_MENU.md)) | Драйвер LCD/подсветки/динамика/флеш для конкретной платы, BLE, USB, DFU |
| 1-битный логический кадр 10×20 + панель справа, независимый от LCD | Выбор панели, MCU, PCB (запрещено AGENTS.md до прохождения hardware-gates) |
| Кросс-сборка ядра под Cortex-M4F как проверка переносимости | Измерение энергопотребления, задержек, времени работы от батареи |

## 2. Слои

```text
   плата / ПК-драйвер ─────────────  bk_hal_t  ─────────────┐
   (кнопки, LCD, динамик, флеш, свет)                         │ 4 порта + system
                                                              ▼
                      ┌──────────────────────── console (firmware application) ────────────────────────┐
                      │ экраны: заставка · меню · настройки · тест кнопок · о приборе · игра            │
                      │ маппинг направлений / ACTION / MODE·SELECT·START → игра и оболочка · рекорды · звук · свет      │
                      └───────┬──────────────────────────┬───────────────────────────┬──────────────────┘
                              │ bk_game_t (vtable)       │ bk_scene_t                │ bk_audio_t, bk_profile_t
                              ▼                          ▼                           ▼
                    games/tetris (правила)      render → bk_frame_t (1 бит)   save (A/B слоты, CRC)
                    ↑ сверка с эталоном на      раскладка 16,5×20 клеток,
                      каждом такте              шрифт, 7-сегментные цифры
```

Зависимости направлены только вниз: игра не знает про консоль, консоль не знает про плату, рендер не знает про LCD.

| Модуль | Файлы | Ответственность |
| --- | --- | --- |
| Базовые типы | `defs.h`, `input.h`, `rng.h`, `event.h` | константы 10×20 / 60 Гц, кнопки и клавиши, детерминированный ГСЧ, события |
| Игра | `game.h`, `core/game.c` | фазы `ready → playing ⇄ paused → over`, счёт/рекорд, скорость/уровень, сценки без ввода, анимация конца игры |
| Tetris | `games/tetris/*`, `brick/games/tetris.h` | правила базового варианта |
| Кадр и рендер | `frame.h`, `render.h`, `font.h` | 1-битный буфер, композиция сцены, шрифты |
| Звук | `audio.h` | события → короткие сигналы, один голос |
| Сохранения | `save.h` | профиль: настройки и рекорды |
| HAL | `hal.h` | единственная граница с «железом» |
| Консоль | `console.h` | конечный автомат приложения |

## 3. Принципы

1. **Детерминизм.** Один вызов `bk_game_step()` — один такт (60 Гц). Одинаковые зерно, режим, скорость, уровень и последовательность ввода дают одинаковые состояния. Единственный источник случайности — `bk_rng_t` (mulberry32, битово совпадает с эталоном). Время нигде не читается из «часов».
2. **Нет кучи и глобального состояния.** Всё состояние игры — POD-структура, первое поле которой `bk_game_t`. Память под неё отдаёт вызывающий (`bk_game_def_t.state_size/state_align`); консоль резервирует `BK_GAME_STATE_MAX` (2048 Б по умолчанию) и проверяет это при `bk_console_init`. Это даёт статическое размещение на MCU и бесплатный воспроизводимый прогон в тестах. Слово «нет глобалов» проверено на ARM: в объектных файлах ядра `.data = 0`, `.bss = 0`.
3. **Игры не играют звук и не рисуют.** Игра отдаёт клетки (`bk_game_cells`, значения `OFF/ON/BLINK`), превью 4×4 и **события** (`BK_EV_*`) в порядке возникновения. Порядок и содержимое событий — часть контракта соответствия.
4. **Логический кадр строго двухуровневый.** `BK_CELL_BLINK` — атрибут «горит и мигает», его разрешает компоновщик по фазе, выведенной из такта (полупериод 15 тактов, как в эталоне). В буфер кадра попадают только «чернила» / «не чернила» (ADR-003, ADR-015).
5. **Кнопки MODE / SELECT / START — дело оболочки.** Игра видит четыре кнопки направлений и одну большую кнопку (как `ROTATE`). `FIRE` (жёсткий сброс) существует в движке, но на корпусе кнопки под него нет (PRD §5).

## 4. Интерфейс игры

Эскиз из [GAME_PORTING.md](GAME_PORTING.md) стал конкретным. Соответствие:

| Эскиз | Реализовано | Комментарий |
| --- | --- | --- |
| `game_init(seed, mode)` | `bk_game_def_t.create(storage, &opt)` | `bk_game_options_t`: seed, hi_score, speed, level, mode |
| `game_tick(pressed, held)` | `bk_game_step(g, &in, &events)` | `bk_input_t { pressed, held }`, события пишутся в переданную очередь |
| `game_frame()` | `bk_game_cells()` + `bk_game_preview()` | клетки 10×20 и превью 4×4, независимы от разрешения LCD |
| `game_pop_audio_events()` | `bk_event_queue_t` (до 16 событий за такт) | переполнение считается (`dropped`) и проверяется тестами |
| `game_serialize()/deserialize()` | **не реализовано** | см. ниже |

**Фазы** повторяют `BrickBase` эталона: `READY → PLAYING ⇄ PAUSED → OVER`. Анимация конца игры (заливка поля снизу вверх, 127 мс на ряд, затем пауза 30 тактов) идёт в фазе `PLAYING`, `OVER` наступает на 183-м такте. Целочисленная арифметика, совпадает с эталоном.

**Сценки без ввода** (в эталоне — замыкания с `done`-колбэками) выражены как пары «вид сценки + прошедшие такты»: игра реализует `scene_frame()` и `scene_done()`, а основа вызывает их в тех же тактах, что эталон. У Tetris единственная сценка — стирание ряда.

**Сериализация состояния игры не сделана намеренно.** Состояние — POD, поэтому снимок «партия на паузе → питание выключено» технически сводится к копированию структуры, но её раскладка зависит от компилятора и версии прошивки, а переносимость между сборками нигде не требуется (PRD требует рекорды и настройки, не продолжение партии). Если продолжение партии понадобится, это отдельный ADR: версия + размер + CRC и сброс при несовпадении сборки.

## 5. HAL: что должна реализовать плата

Все указатели необязательны (`NULL` — порт пропускается), поэтому тесты и «безголовые» прогоны тривиальны.

| Порт | Функции | Контракт |
| --- | --- | --- |
| input | `read_buttons()` → маска `bk_button_t` | раз в такт, антидребезг на стороне драйвера |
| display | `present(frame)`, `max_fps` | вызывается **только если картинка изменилась и панель может её принять**; кадр — позитивная полярность, 1 бит/точка, MSB первым. `max_fps` — предел частоты **новых** картинок (0 — без предела): промежуточные кадры пропускаются, всегда уходит последний |
| audio | `set_tone(hz)` | один меандр, 0 — тишина; громкость — физическое колесо, ядру не видна (ADR-007: только встроенный динамик) |
| storage | `read(slot)`, `write(slot)` | два слота до 1024 Б; драйвер отвечает за стирание страниц/износ; ядро хранит CRC и номер последовательности |
| system | `set_frontlight(level)`, `entropy()` | уровни света 0…2 (отображение в ШИМ — дело драйвера); энтропия для зёрен партий |

**60 Гц — частота симуляции, не панели** (AGENTS.md: «Never assume 60 Hz»; у кандидата LS032B7DD02 в документации `fSCS` 1…10 Гц). Консоль каждый такт собирает кадр, сравнивает с показанным и отдаёт панели не чаще `max_fps`; пропуски считаются (`dropped_frames`), интервал — `ceil(60 / max_fps)` тактов (10/15/20/30 кадров/с → 6/4/3/2). Что это даёт игре — [UI_MENU.md §7](UI_MENU.md): расчёт, не измерение.

Что произойдёт на плате, не выбрано: частота опроса, способ получения 60 Гц (таймер/RTC), сон между тактами, режим обновления панели — всё это решается на этапе выбора дисплея и MCU (HARDWARE_RESEARCH.md, gates 1–4).

## 6. Рендер и раскладка (ADR-016, ADR-026)

* Игровое поле — всегда **10 × 20 квадратных клеток**, **статусная панель — справа** (счёт, рекорд, NEXT 4×4, SPEED, LEVEL, значки звука и паузы). Клетки квадратные при любой раскладке, панель не уходит под поле.
* Две раскладки. **Эталонная сетка** `bk_layout_init(cell)`: чётное `cell` = 8…16 точек на клетку, экран 16,5 × 20 клеток (панель 6,5 клетки), при 8 — 132×160 точек; на ней построены golden-кадры. **Подгонка под панель** `bk_layout_fit(width, height)`: наибольшая целая клетка, при которой поле помещается, **всё оставшееся справа — статус-колонке**, поле центрируется по вертикали, NEXT уменьшается до ширины колонки, цифры и подписи пересчитываются. Нативное разрешение **не выбрано**; из кандидатов `DISPLAY_CANDIDATES.md` получается клетка 26 точек и колонка 76 точек (3.16″, 336×536), 16 и 80 (4.4″ повёрнутый), 20 и 40 (2.7″ повёрнутый) — [UI_MENU.md §6](UI_MENU.md), там же физические размеры в мм (арифметика) и вывод о читаемости. Драйвер может дополнительно масштабировать кадр целым коэффициентом и добавлять **светлые** поля (на позитивной панели поля — фон, не чернила).
* Размер буфера кадра — параметр сборки `BRICK_FRAME_MAX_W/H` (по умолчанию 336×536, самый большой из кандидатов; это резерв RAM, а не выбор панели).
* Клетка при шаге ≥ 8 рисуется как контур + зазор + ядро (классический вид), без «призрачных» неактивных клеток: третьего уровня в кадре нет.
* Текст — встроенный шрифт 3×5, только латиница (локализация не требуется PRD; для кириллицы понадобится шрифт 5×7 — отдельное решение). Крупные цифры/буквы 4×7 клеток для номера игры в меню и мелкие цифры 3×5 для номера режима взяты из эталона (`menuArt.ts`), см. [THIRD_PARTY.md](../THIRD_PARTY.md).
* Контраст, отражательная способность, подсветка и читаемость при выключенном свете **не моделируются**: PNG в `docs/img` — лишь иллюстрация логического кадра.

## 7. Звук (ADR-007)

Игры и меню генерируют события, `bk_audio_cue_for_event()` сопоставляет им сигнал, `bk_audio_t` проигрывает его на одном голосе с приоритетами (более важный сигнал не прерывается менее важным; программное отключение звука обрывает сигнал сразу). Секвенсор тактируется тем же 60-герцовым тактом.

**Все тона — временные заглушки** (оригинальные короткие фразы, не транскрипция прошивок и не мелодии донора). Окончательный звуковой дизайн и акустика требуют реального динамика и камеры.

## 8. Сохранения (ADR-028)

Профиль (настройки, позиция меню, до 96 рекордов «игра + режим») хранится как запись `BKSV | версия | длина | seq | полезная нагрузка | CRC-32` в **явном little-endian**, а не дампом структуры. Запись идёт в тот слот, где **нет** самой свежей валидной копии; при обрыве питания предыдущая копия цела. Неизвестная версия игнорируется (значения по умолчанию), порча обнаруживается CRC (тест искажает каждый байт записи по очереди). Рекорды никогда не вытесняются молча: при переполнении `set_record` возвращает `false`.

## 9. Память и размер (компиляция, не измерение на железе)

Сборка: `arm-none-eabi-gcc 13.2.1`, `-mcpu=cortex-m4 -mthumb -mfloat-abi=hard -mfpu=fpv4-sp-d16 -Os`, `cmake/arm-none-eabi.cmake`, цель `brickcore_size`.

| Что | Значение |
| --- | --- |
| Ядро целиком (12 модулей, включая шрифты, Tetris и консоль), `.text` | ≈ 23,5 КБ |
| `.data` / `.bss` ядра | 0 / 0 |
| `sizeof(bk_console_t)`, буфер кадра 336×536 (умолчание) | 48 448 Б (два кадра по 22 518 Б) |
| `sizeof(bk_console_t)`, буфер кадра 264×320 | 24 544 Б (два кадра по 10 566 Б) |
| `sizeof(bk_console_t)`, буфер кадра 132×160 | 8 864 Б (два кадра по 2 726 Б) |
| состояние Tetris (`bkt_game_t`) | 552 Б |
| профиль (`bk_profile_t`) | 788 Б |
| внешние символы libc/libm | `memcpy memmove memset memcmp strlen strncpy fmod` и soft-double (`__aeabi_dmul/ddiv/dsub/dcmpge/l2d/ui2d`) |

Ни `malloc`, ни `printf` ядру не нужны. Soft-double и `fmod` появляются из-за таймера гравитации, оставленного в `double` ради побитового соответствия эталону (ADR-024); вызываются они только на шаге гравитации, не на каждый пиксель. Это **компиляционная** оценка: на плате размер, скорость и энергопотребление не измерены.

## 10. Порт на nRF52840 или другой ARM MCU

Кандидаты и проверки железа — в HARDWARE_RESEARCH.md; ниже только программная часть.

1. **Такт.** Нужен источник события раз в 1/60 с (таймер/RTC); тело цикла: `bk_console_tick(&console)` и сон до следующего такта. Дробные периоды гравитации уже учтены внутри игры, джиттер такта влияет на ощущения, но не на правила.
2. **Порты HAL.** Реализовать пять структур из `hal.h`. Для Memory LCD драйвер получает `bk_frame_t` целиком и может отправлять только изменившиеся строки (сравнить с предыдущим кадром); порядок бит и инверсия (VCOM, полярность) — внутри драйвера.
3. **Сборка.** Добавить стартовый код, скрипт линковки и SDK платы; ядро подключается как статическая библиотека `brickcore` (`firmware/CMakeLists.txt`), без изменений исходников. `BRICK_FRAME_MAX_W/H` (буфер кадра, **два** экземпляра в консоли) и `BK_GAME_STATE_MAX` задают объём RAM; в `bk_display_port_t.max_fps` указать предел обновления панели.
4. **Проверка.** До выхода на плату прогнать на хосте `ctest` (в т.ч. соответствие эталону), затем повторить сверку на целевом процессоре: **расчёт `double` и `fmod` на Cortex-M4F в этом PR не запускался** (только компиляция); сверка должна подтвердить, что soft-double даёт те же результаты, что IEEE-754 на хосте (ожидаемо, но не проверено).
5. **Не сделано и не выбрано:** BLE, USB/DFU, загрузчик, управление питанием и сном, измерение энергопотребления и задержки кадра. Отдельно: ядро собирает кадр **каждый такт** и только потом сравнивает с показанным; стоимость этой композиции на MCU не измерена (риск R-8), оптимизация (рендер по флагу изменения, грязные строки для Memory LCD) не реализована.

## 11. Как добавить игру

1. Выбрать **точный** идентификатор в реестре эталона и записать уровень достоверности: верифицированная ROM-реализация или приближение (AGENTS.md требует явной пометки).
2. Проверить лицензии кода и ассетов (THIRD_PARTY.md) до копирования чего-либо.
3. Создать `firmware/games/<name>/`: структура с `bk_game_t base` первым полем, `bk_game_vtable_t`, `bk_game_def_t` с **новым уникальным** `uid` (uid в сохранениях не переиспользуются и не перенумеровываются).
4. Добавить запись `{def, glyph}` в каталог изделия `firmware/catalog/catalog.c` (`bk_catalog_entry_t`, 1–2 символа: цифра или буква); его же используют симулятор и будущий образ прошивки.
5. Расширить `tools/conformance/export_tetris.ts` до экспортёра игры (или добавить соседний), сгенерировать фикстуры, добавить раннер; без побитово сверяемой трассы порт игры не считается завершённым.
6. Юнит-тесты правил (как `tests/unit/test_tetris_rules.c`), событие→сигнал в `audio.c`, миниатюра для меню, строка в UI_MENU.md и ADR при расхождении с эталоном.
7. Для игр, которым нужна отдельная кнопка огня (`BK_GAME_USES_FIRE`), решение о раскладке на единственную кнопку действия — отдельный ADR (PRD §5).

## 11а. Каталог игр и симулятор

`firmware/catalog/catalog.c` (библиотека `brickcatalog`) перечисляет игры изделия в порядке меню; ядро (`brickcore`) этого не знает. `platform/sim/` — драйвер без окна и фронтенды для терминала и браузера (WebAssembly без libc); подробности, запуск и проверки — [SIMULATOR.md](SIMULATOR.md). Платформенный код (`platform/`) не входит в образ прошивки и в кросс-сборку Cortex-M4F.

## 12. Открытые вопросы

* Панель и разрешение: когда они будут выбраны, раскладка пересчитается `bk_layout_fit` — это параметр, а не переделка; но читаемость цифр и подписей на узкой статус-колонке (3.16″: 9,7 мм, цифры 1,0 × 1,9 мм) надо проверять на образце, и число цифр счёта (7 по эталону) — решение владельца.
* Скорость обновления панели (`max_fps`) и играбельность при 10/15/20/30 Гц — гейт FPS из DISPLAY_CANDIDATES.md, измерений нет.
* Назначение кнопок MODE / SELECT / START (физический набор подтверждён PRD), быстрый доступ к подсветке, подтверждение выхода — [UI_MENU.md](UI_MENU.md), ADR-025.
* Два полных буфера кадра (рендер и «показано») дают 45 КБ при 336×536; вместо второго буфера возможно построчное сравнение/хэши — оптимизация не сделана (R-8).
* Целочисленный таймер гравитации вместо `double` — ADR-024, нужен допуск ≤ 1 такта расхождения с эталоном.
* Продолжение партии после выключения питания (раздел 4).
