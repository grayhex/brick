# Соответствие порта эталону (conformance harness)

Цель — доказуемо, а не «на глаз», что C-порт играет так же, как TypeScript-эталон [ApolloBrickGames](https://github.com/grayhex/ApolloBrickGames). Процесс следует [GAME_PORTING.md §4](GAME_PORTING.md): фиксированное зерно, записанные трассы ввода, сохранённые ожидаемые состояния в JSON, прогон тех же трасс на C-ядре без графики и звука.

> **Что это не доказывает.** Эталон — не ROM оригинала: совпадение с ним означает «порт делает то же, что эталон», а не «совпадает с настоящим устройством» ([GAME_TETRIS.md §2, §4](GAME_TETRIS.md)). Звуковые тона и графика здесь не сверяются (проверяются события и клетки, не пиксели LCD).

## 1. Как это устроено

```text
  ApolloBrickGames @ закреплённый коммит ──(исполняется, не переписывается)──▶ tools/conformance/export_<игра>.ts
                                                                                        │   (общий код: lib.ts)
                                    tests/fixtures/<игра>/<игра>.conformance.json ◀─────┘  (генерируется, руками не правится)
                                                                │
        tests/conformance/test_<игра>_conformance.c ── tests/support/conf_runner.c ── C-ядро, те же входы ── дайджест на КАЖДОМ такте
```

* Экспортёр собирается `esbuild` вместе с исходниками эталона (read-only checkout) и прогоняет **настоящий** `Lab`/`Bot` эталона; на каждом такте считает дайджест состояния. Всё общее (запись такта, дайджест, сценарные операции ввода, разбор `--out`/`--dump`, сборка JSON) лежит в `tools/conformance/lib.ts`; экспортёр игры задаёт только свои сценарии и свои операции подготовки поля.
* C-раннер `tests/support/conf_runner.c` читает те же трассы (ввод + операции подготовки поля) и сверяет дайджест после каждого такта. Игра подключается описанием `conf_game_t {имя, размер стенда, init, game_of, apply_op}`: раннер не знает правил, операции подготовки (`wipe`, `fill`, `snake`, `food`, …) выполняет «стенд» игры (`tests/support/tetris_lab.c`, `snake_lab.c`). На первом расхождении раннер печатает номер такта, оба дайджеста, состояние C (поле, события) и останавливает сценарий.
* Нужен только **Node ≥ 20 для регенерации** фикстур; сами C-тесты Node не запускают.

Закреплённая версия эталона записана в самом файле (`reference.commit`) — сейчас `abd7c3426f28222b54db2fe280597d7578e7191c`. Игры: **Tetris**, **Snake** и **Racing**, у каждой один вариант (ADR-036).

## 2. Формат `brick-conformance/1`

Файл JSON: `format`, `game`, `reference {repo, commit, files}`, `rng`, статические секции игры (Tetris: `catalog`, `fallTicks`; Snake: `periods`), `scenarios[]`.

| Секция | Содержимое | Проверка в C |
| --- | --- | --- |
| `rng` | для 5 зёрен — последовательность `next`/`int`/`chance` (Snake: только `int`, в том числе с границей 1, которая не тратит число) | `bk_rng_*` выдаёт те же числа |
| `catalog` | 7 фигур × 4 угла: клетки и границы после выравнивания | `bkt_piece_make` |
| `fallTicks` (Tetris) | период гравитации (double) на скоростях 1…10 | **точное равенство** double |
| `periods` (Snake) | период шага (double, в тактах) на скоростях 1…10 | **точное равенство** double |
| `scenarios[]` | см. ниже | побитовое соответствие на каждом такте |

**Сценарий:** `name`, `description`, `options {seed, speed, level, hiScore}`, `ticks`, `trace`, `digests`, `checkpoints`, `final`.

* **`trace`** — список записей двух видов. `[код, число]` — код такта, повторённый `число` раз. Остальное — операции подготовки состояния (методы `Lab` эталона), выполняемые между тактами. Tetris: `["wipe"]`, `["fill", y, "####..####"]`, `["put", "Square", угол, x, y]`, `["setNext", …]`, `["respawn", …]`, `["dueFall"]`, `["poke", очки]`. Snake: `["snake", направление, клетки…]` (положение червяка), `["food", клетка]`, `["eaten", число]`, `["timer", остаток]`, `["lives", число]`, `["poke", очки]`.
* **Код такта** = `held` (биты 0–5) `|` `pressed << 6` `|` `команда << 12`. Биты клавиш как в `bk_key_t`: влево 1, вправо 2, вверх 4, вниз 8, поворот 16, огонь 32. Команды: 1 `start`, 2 `pause`, 3 `resume`, 4 `restart`. Явный `pressed` нужен, чтобы воспроизводить и «нефронтовые» нажатия из тестов эталона.
* События перед такта-шагом от операций подготовки (например, `respawn` с концом игры) остаются в очереди до следующего обычного шага, как в эталоне; раннер это воспроизводит и отвергает остальные случаи.
* **`digests`** — по 4 hex-символа на такт (16 бит). **`checkpoints`** — полный 32-битный дайджест каждые 250 тактов. **`final`** — итоговое состояние читаемо: поле построчно, превью, счёт, скорость, число событий по типам.

### Дайджест (FNV-1a, 32 бита; в файле на такт хранится `h ^ (h >> 16)` & 0xFFFF)

Порядок байт, все многобайтовые поля little-endian: `tick:u32`, `phase:u8` (0 ready, 1 playing, 2 paused, 3 over), `score:u32`, `hiScore:u32`, `speed:u8`, `level:u8`, `lives:u8` (255 — нет), `overFill:u8`, 200 клеток `u8` (0/1/2, как `bk_game_cells`), `hasPreview:u8` и, если есть, 16 байт превью, число событий `u8`, затем каждое событие `type:u8, a:u8, b:u16, c:u32` (номера событий — `bk_event_type_t`; для `lines` `a` — число рядов, `c` — маска экранных рядов; для `levelUp` `a` — скорость).

16 бит на такт достаточно для обнаружения: после реального расхождения состояния различаются на всех последующих тактах, поэтому шанс скрыть его целиком ничтожен; ловится и однотактовое расхождение (шанс пропуска ≈ 1/65536 на такт), а контрольные точки в 32 бита страхуют длинные участки.

## 4. Запуск

```sh
cmake -S . -B build -G Ninja && cmake --build build && ctest --test-dir build --output-on-failure
./build/tests/test_tetris_conformance tests/fixtures/tetris/tetris.conformance.json   # подробный вывод
./build/tests/test_snake_conformance tests/fixtures/snake/snake.conformance.json
./build/tests/test_racing_conformance tests/fixtures/racing/racing.conformance.json
```

Регенерация фикстур (нужен чистый checkout эталона на закреплённом коммите):

```sh
git clone https://github.com/grayhex/ApolloBrickGames /tmp/ApolloBrickGames
git -C /tmp/ApolloBrickGames checkout abd7c3426f28222b54db2fe280597d7578e7191c
cd tools/conformance && npm ci
APOLLO_BRICK_GAMES=/tmp/ApolloBrickGames npm run export:tetris
APOLLO_BRICK_GAMES=/tmp/ApolloBrickGames npm run export:snake
APOLLO_BRICK_GAMES=/tmp/ApolloBrickGames npm run export:racing
git diff --exit-code ../../tests/fixtures      # на закреплённом коммите файл должен совпасть побайтно
```

Отладка расхождения: `node dist/export_<игра>.mjs --dump <сценарий> --tick <N>` печатает состояние эталона по тактам; раннер печатает состояние C на том же такте. Экспортёр детерминирован: два запуска дают побайтно одинаковый файл, он же совпал с закоммиченным; задание `fixtures` в CI заново генерирует оба файла на закреплённом коммите и сравнивает их `cmp` с закоммиченными. Рефакторинг экспортёра при добавлении Snake (общий `lib.ts`) оставил фикстуру Tetris побайтно прежней.

## 5. Проверка самой проверки (мутационные прогоны)

Тест, который «всегда зелёный», ничего не стоит, поэтому в C-код намеренно вносились ошибки; каждая была поймана, исходный код восстановлен.

| Внесённая ошибка | Как поймана |
| --- | --- |
| очки за 4-й ряд 8 → 9 | расхождение на 120-м такте `lines-4` |
| задержка автоповтора 8 → 9 тактов | `left-autorepeat`, такт 21 |
| элемент таблицы B0202 82 → 83 | `fallTicks` и такт 43 |

## 6. Ограничения и риски

* **Платформа вычислений.** Таймер гравитации использует IEEE-754 `double` и `fmod` ради побитового совпадения (ADR-024); для этого ядро собирается с `-ffp-contract=off`. На хосте (gcc, clang, ASan/UBSan) расхождений нет. **На Cortex-M4F вычисление не запускалось** (только компиляция): soft-double обязан давать те же результаты по стандарту, но это нужно подтвердить прогоном на целевом процессоре или эмуляторе (риск R-1).
* Эталон — симулятор, а не ROM (см. выше); неизвестное в нём (допущения) переносится как есть.
* Покрыты Tetris, Snake и Racing, каждая в одном варианте. Остальные 50 вариантов Tetris, вариант «FRAME» у Snake (был в коде, убран по ADR-036), Pentix и остальные игры не портированы и не покрыты.
* **Snake: 13 плодов и +100 — адаптация самого эталона** ([GAME_SNAKE.md](GAME_SNAKE.md)); совпадение с эталоном по этим правилам не доказывает совпадения с настоящей игрой.
* Фикстура Snake проверяет порядок случайных чисел для места плода на уровне «одно обращение к `rng`, выбор по списку свободных клеток»; сам эталон выбирает через `rng.pick`, а в настоящей прошивке место плода берётся с таймера — это допущение.
* Сверяются состояния и события, но не звук (тоны) и не пиксели LCD: для них есть золотые кадры ([UI_MENU.md](UI_MENU.md)) и нет ни одной проверки на железе.

## 7. Как добавить игру или вариант

1. `tools/conformance/export_<игра>.ts`: сценарии и операции подготовки поля поверх `lib.ts` (`Recorder`, `runExporter`); добавить имя игры в `build.mjs` и скрипт `export:<игра>` в `package.json`.
2. Сгенерировать фикстуру на закреплённом коммите: `tests/fixtures/<игра>/<игра>.conformance.json`.
3. Стенд игры `tests/support/<игра>_lab.[ch]` (подготовка состояния теми же операциями, что в эталоне) и `tests/conformance/test_<игра>_conformance.c` с описанием `conf_game_t`; зарегистрировать в `tests/CMakeLists.txt`.
4. Добавить игру в проверку воспроизводимости в `.github/workflows/ci.yml` (задание `fixtures`).
5. Мутационные прогоны для новой логики и таблица в §5. Без трассы, сверяемой на каждом такте, порт не считается завершённым ([FIRMWARE_ARCHITECTURE.md §11](FIRMWARE_ARCHITECTURE.md)).
