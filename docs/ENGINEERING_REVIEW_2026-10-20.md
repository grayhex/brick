## Высокоприоритетные технические риски

### P0 / необходимость аппаратной проверки — Sharp LCD 3.16

Для LCD-кандидата `LS032B7DD02` расчёт `bk_layout_fit(336,536)` дает поле 10×20 клеток по 26 px, а справа только **76 px** (~9,65 мм). По расчёту `panel_fit.c` шрифт цифр счёта около **1,02×1,91 мм**. Это **не одобрение читаемости**. Кроме того в документации Sharp приводится `fSCS=1–10 Гц`, смысл ограничения относительно реальных перерисовок необходимо уточнить. Даже правильный `max_fps` не сделает анимацию приемлемой, если физическая панель не годится для Tanks/Racing. Не фиксировать дисплей/размер PCB без тестового образца. См. [DISPLAY_CANDIDATES](DISPLAY_CANDIDATES.md).

Предлагаемый критерий первого теста: видимые с рук, с обычного расстояния счета/уровни и NEXT; Tetris/Tanks на 10/15/20/30 кадрах/сек; белый свет выключен и на минимуме. **Параметры читаемости пока не имеют утвержденного численного порога.** Рекомендуется испытать одновременно native 26px cell и компромисс с меньшим размером клетки, чтобы увеличить правую панель (переход не делать без одобрения вида экрана).

### P1 — CPU/память и батарея

- `bk_console_tick` пересобирает полный 1-битный кадр **каждые 1/60 секунды**, хотя из-за ограничения FPS на панель отправляются реже. Это может расходовать лишние CPU-такты/энергию на 64 MHz MCU. Измерить на целевом процессоре, затем оптимизировать UI dirty rectangles/изменения сцен, либо откладывать композицию до кадра показа.
- В консоли **две** копии кадра `BK_FRAME_MAX_W/H`, по умолчанию 336×536: 22 512 байт × 2 = **45 024 байта RAM**, без game state, стека SDK/BLE и runtime. `.bss = 0` для *статической библиотеки* не означает, что конечная прошивка использует ноль RAM. Составить карту памяти после линковки полной BLE прошивки.
- В таймере Tetris используются `double` и `fmod` для точного совпадения с эталоном. Кросс-сборка `.a` **не** проверяет финальную линковку библиотеки `libm`, время исполнения и точное совпадение на Cortex-M4. Пока допустимо ради воспроизводимости; измерить.

### P1 — управление и аудио

- **Одна Action-кнопка не даёт прямого вызова `FIRE`** (hard drop), хотя Tetris-движок содержит команду. Это сознательное проектное ограничение; проверить UX игр, для которых FIRE/ROTATE независимы. Не вводить новые кнопки без согласования.
- Звуковые сигналы сейчас **временные, один прямоугольный тон**. Спецификация говорит о качественном звучании; динамик/усилитель, тембры, громкость, вибрации (если вообще нужны) ещё не спроектированы. Не считать аудиотрек завершённым.
- Выход из теста кнопок через одновременное `MODE+SELECT+START` задействует три кнопки под экраном: проверить эргономику физического прототипа.

### P2 — CI и эксплуатация

- Два события `push` и `pull_request` ранее создавали двойные прогоны в feature-ветках. В `.github/workflows/ci.yml` оставить `push` **только для main** и `pull_request` для PR; cancel-in-progress не завершённых старых запусков. Новый YAML ещё должен пройти следующий CI после изменения.
- Профиль сохраняется в 2 чередующиеся слота; реальный flash-драйвер должен реализовать атомарность/wear leveling. Изменение подсветки сейчас вызывает сохранение профиля немедленно: оценить число циклов Flash и добавить debounce/batched save при реализации.
- Для начала интерактивных UX-тестов нужен **живой ПК-симулятор** с теми же 8 аппаратными кнопками; golden-картинки полезны, но не позволяют почувствовать задержки, последовательность нажатий и структуру меню.

## Что НЕ менять без подтверждения

- Геометрию игрового стакана **10×20**, раздельные жёлтые направления, единственную Action, положение функций под LCD, только фронтальную центральную решётку динамика.
- Аппаратную платформу и финальный экран считать **кандидатами**, а не выбранными платой.
- Не ускорять Tetris заменой `fmod` на целочисленную математику без эквивалентных conformance-тестов.
- Не выдавать `-ffp-contract=off` и кросс-компиляцию за аппаратную валидацию.

## Следующие действия

1. Интерактивный desktop-прототип (SDL2/SDL3 либо лёгкий GUI поверх той же C библиотеки), физическая раскладка 8 кнопок, симуляция экрана 10/15/20/30 Гц с сохранением 60 Гц игровой логики.
2. Измерить читаемость в натуральном масштабе на кандидатах LCD и выбрать минимальную ширину статусной области на экране (в мм).
3. На Cortex-M4F проверить связку `libm` + soft-double, CPU/стек, frame compose.
4. После CAD корпуса и подтверждённого дисплея начинать аппаратный HAL, BLE GATT, USB DFU, управление питанием.
5. По отдельной задаче оценить, какие будущие игры требуют независимого FIRE (кнопки теперь утверждены).

**Вывод:** значимых логических противоречий C ядра утверждённой конфигурации корпуса в просмотренных интерфейсах не обнаружено; остались подтверждаемые инженерные риски, незавершённые компоненты и UX-решения.
